## Environment limitation (why this is "best feasible", not a true 0/0 proof)

A true `0 destroy / 0 create` confirmation for the `moved {}` blocks requires a
**populated v0.4.16 state** containing the OLD resource addresses
(`module.bedrock_llm_processor[0].aws_lambda_function.*`, etc.). `moved {}` notes
only render in a plan when the `from` address actually exists in state.

No representative v0.4.16 state is available in this environment:

- The example working directory's `terraform.tfstate` is **empty** (0 resource
  entries, serial 898).
- No AWS credentials / network are available, so a refreshed plan against live
  infrastructure is not possible (the plan stops at `STS GetCallerIdentity` →
  `InvalidClientTokenId` once it reaches the first credential-backed data source).

Per breaking-changes.md and the migration guide, applying against a real
v0.4.16 state and confirming the 0/0 move counts is therefore an **operator
step**, documented in `docs/migration-v0.4.16-to-v0.5.12.md`.

## What WAS demonstrated

Running `terraform plan -refresh=false` against an empty state plans the
credential-independent resources (random/null/local_file/terraform_data) before
hitting the STS error. This proves:

1. **The configuration is internally consistent and plannable** — the root
   composition, façade modules, nested `module.engine`, and feature-plugin
   wiring all evaluate.
2. **The façade→engine nesting is correct** — engine resources render at
   `module.genai_idp_accelerator.module.bedrock_llm_processor[0].module.engine.*`,
   exactly the `to` addresses the `moved {}` blocks target.
3. **`Plan: 38 to add, 0 to change, 0 to destroy`** for the planned subset on a
   green-field (empty) state — i.e. a fresh deploy. On an existing v0.4.16 state
   the `moved {}` blocks are what convert these would-be create/destroy pairs
   into in-place moves.

## `moved {}` intent (from `moved.tf`)

The 98 `moved {}` blocks target **0 destroy / 0 create** for stateful resources.

### Processor façade refactor (83 blocks)

The per-pattern modules (`module.bda_processor`, `module.bedrock_llm_processor`,
`module.sagemaker_udop_processor`) became thin façades that delegate the engine
to a shared internal submodule `module.engine`
(`modules/processors/unified-processor/`). Inner resources that lived directly
under each façade now live one level deeper under
`module.<facade>[0].module.engine.*`.

| Façade | `moved` blocks | Mapping quality |
|---|---|---|
| `bedrock_llm_processor` | 67 | Clean 1:1 — engine derived 1:1 from the former bedrock-llm module; every resource maps to the identically-named engine resource one level deeper. |
| `bda_processor` | 8 | Stateful subset preserved (SQS DLQ, SFN state machine, the BDA/results/summarization/evaluation Lambdas, KMS policy + attachment). ECR/CodeBuild/EventBridge resources with no engine equivalent are **unavoidable recreates** (documented in the migration guide with impact + rollback). |
| `sagemaker_udop_processor` | 8 | Stateful subset preserved (SFN state machine, evaluation/assessment Lambda + IAM/log group). Pattern-3-only ECR/CodeBuild/`*_function` resources are **unavoidable recreates** (migration guide). |

The engine's new-only resource (`time_sleep.wait_for_iam_propagation`) has no
prior address, so it intentionally carries no `moved {}` block (it is a genuine
create).

### MCP relocation + v0.5.3 rename (15 blocks)

The MCP stack moved OUT of `module.processing_environment_api` INTO the new
`module.mcp_integration` feature submodule, and the Lambda was renamed
`agentcore_analytics_processor` → `agentcore_mcp_handler`. The deployed
`function_name` is intentionally held at the legacy value
(`<api_name>-agentcore-analytics-proc`) so the rename is an in-place update
(`function_name` is ForceNew) — keeping the move at 0 destroy / 0 create.

## MCP `moved {}` plan-test (task 10.3, Req 8.2 / Property 4)

Task 14.2 (above) captures the whole-refactor plan artifact. This section is the
**focused, reproducible plan-test for the MCP Lambda relocation + rename**
specifically — the `agentcore_analytics_processor` → `agentcore_mcp_handler`
move out of `module.processing_environment_api` into `module.mcp_integration`.

Run it with:

```bash
genai-idp-terraform/scripts/test-mcp-moved.sh            # offline (default)
genai-idp-terraform/scripts/test-mcp-moved.sh --state path/to/v0.4.16.tfstate  # operator
```

### Why a true 0/0 proof needs operator state

A `moved {}` note only renders in a plan when the `from` address actually exists
in state. The authoritative confirmation therefore needs a **populated v0.4.16
state** carrying the OLD address
`module.processing_environment_api[0].aws_lambda_function.agentcore_analytics_processor[0]`.
That state is **not available offline** in this repo (the example state is empty
— serial 898, 0 resources — and no AWS creds/network are present, so the root
plan stops at `STS GetCallerIdentity`). This is the same limitation the 14.2
agent documented. Confirming the live 0/0 counts is an **operator step** (mode
`[C]` below), also recorded in `docs/migration-v0.4.16-to-v0.5.12.md`.

### What the script does (best feasible, three layers)

| Layer | Needs creds? | What it proves |
|---|---|---|
| **[A] Offline self-test** | no | Builds a synthetic fixture that mirrors the **exact address shape** of the real MCP move — a count-gated `processing_environment_api[0]` child module holding `agentcore_analytics_processor[0]`, relocated+renamed to a count-gated `mcp_integration[0]` child module holding `agentcore_mcp_handler[0]`, with an identically-formed `moved {}` block. Seeds state with the OLD address, switches config, and asserts the plan reports a **move** with **0 add / 0 change / 0 destroy** (and a clean re-plan after apply). Exercises the moved-block engine across a module boundary + count index + resource rename — the precise transformation the real block performs. |
| **[B] Address cross-check** | no | Parses every `to = module.mcp_integration[0]....` address out of `moved.tf` and asserts a matching `resource "<type>" "<label>"` exists in `modules/features/mcp-integration/`; asserts the Lambda rename mapping and that every MCP `from =` originates in `module.processing_environment_api[0]`; and asserts the legacy `function_name` (`${api_name}-agentcore-analytics-proc`) is preserved (what makes the rename an in-place update). |
| **[C] Operator mode** (`--state`) | yes | Runs the **real** root `terraform plan` against a supplied representative v0.4.16 state and greps the actual MCP addresses for 0 destroy / 0 create. The authoritative proof. |

### Address cross-check result (offline, layer [B])

All checks pass:

- **15 / 15** MCP `to = module.mcp_integration[0]....` addresses map to a real
  `resource` in `modules/features/mcp-integration/` (Lambda, IAM role/policy/
  attachments incl. `_xray` + `_vpc`, log group, gateway-manager Lambda + role +
  policy + log group + build `null_resource`, gateway-execution role + policy,
  the `aws_cloudformation_stack.agentcore_gateway`, and both
  `aws_cognito_user_pool_client` clients).
- The Lambda rename mapping is present and exact:
  `module.processing_environment_api[0].aws_lambda_function.agentcore_analytics_processor[0]`
  → `module.mcp_integration[0].aws_lambda_function.agentcore_mcp_handler[0]`.
- All MCP `from =` addresses originate in `module.processing_environment_api[0]`
  (the relocation source).
- The legacy `function_name` is held constant, so the rename is an in-place
  update (`function_name` is ForceNew) — not a destroy/recreate.
